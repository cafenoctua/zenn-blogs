## はじめに

最近、自分がよく使っているデータ変換ツール **dbt** の新バージョンが **dbt-fusion** という名前でリリースされた。このツールはRustで書かれており、処理速度が大幅に向上したことで注目を集めている。また、Google Cloud SDKもRustをサポートし始め、業務でRustに触れるタイミングが近づいている実感があった。

これまでのプログラミング言語遍歴はこんな感じ：

| 言語   | 使ったシーン               |
| ------ | -------------------------- |
| C言語  | 学生時代                   |
| C++    | 学生時代                   |
| VBA    | 社会人初期                 |
| Python | データエンジニアリング全般 |
| JS/TS  | フロントエンド・スクリプト |
| Java   | 業務システム               |

Rustはまだ触ったことがなかったが「いつかやらなければ」が「今だ」になったので、学習を始めた。

## 学習方法：Claude Code Learning modeを専属教師として使う

### 従来の言語学習の流れ

新しい言語を学ぶとき、自分はだいたい以下の流れをたどっていた。

1. 公式ドキュメントのGet Startedを読む
2. 本や動画で体系的に学ぶ
3. 何か作りながら覚える

この方法は悪くないが、「本を読むだけでふーんで終わる」フェーズが長くなりがちで、実際に書けるようになるまでに時間がかかる。

### Claude Code Learning modeを組み合わせる

今回はAIを学習に組み込んだ。とはいえ最初からAIに頼りすぎると、コンセプトを理解しないままコードを書かされる感覚になるので、**まず基礎は自分で教材を読んだ**。

使った教材：

- [The Rust Programming Language（英語）](https://doc.rust-lang.org/book/)
- [Rust入門（日本語版）](https://doc.rust-jp.rs/book-ja/ch03-00-introduction.html)

教材を読んだあと、Claude CodeのLearning modeを使って以下のサイクルを回した。

```
教材でトピックを読む
    ↓
Claude君に練習問題をいくつか作ってもらう
    ↓
自分で解く
    ↓
Claude君に提出して評価・フィードバックをもらう
    ↓
次のトピックへ
```

この「インプット → 問題作成 → 自力で解く → 評価」のサイクルが効いた。疑問はすぐ聞けるし、「この書き方はRustらしくない」というフィードバックも即座にもらえる。

## 実践アプリ：dbt-impact を作る

基礎を一通り終えた段階で、実際のツールを作ることにした。「業務で使えるもの」というコンセプトで考えたとき、dbtのDAG（有向非巡回グラフ）をCLIで解析するツールが浮かんだ。

### 解決したかった課題

dbtでデータ変換パイプラインを作ると、モデル（SQLファイル）が互いに依存し合うDAGができる。「このモデルのロジックを変えたとき、下流の何が影響を受けるか」を手動でDAGを追って確認するのが辛かった。

`manifest.json`（dbtのビルド成果物）には依存関係が記録されているので、これをパースしてCLIで即座に影響範囲を出力するツールを作ることにした。それが **dbt-impact** だ。

### コマンド仕様

```bash
# 下流への影響（このモデルに依存しているものをすべて出す）
dbt-impact downstream stg_jaffle_shop_payment

# 上流への依存（このモデルが依存しているものをすべて出す）
dbt-impact upstream dim_customers --depth 2 --format tree
```

出力例（tree形式）：

```
stg_jaffle_shop_payment
└── dim_customers
    └── analysis.check_dim_customers
```

### アーキテクチャ

プロジェクト開始前に、Claude君と一緒に設計を詰めた。責任分離を意識して5つのモジュールに分割した。

```
src/
├── main.rs      CLIエントリポイント（clapでサブコマンドをパース）
├── manifest.rs  manifest.json の構造体定義・デシリアライズ
├── graph.rs     依存グラフの構築・BFS探索
├── output.rs    List / Tree / JSON の出力フォーマッター
└── error.rs     カスタムエラー型の定義
```

使用したクレート：

| クレート               | 用途                             |
| ---------------------- | -------------------------------- |
| `clap`                 | CLIパース（`#[derive(Parser)]`） |
| `serde` + `serde_json` | manifest.jsonのデシリアライズ    |
| `thiserror`            | カスタムエラー型の定義           |

## 実装で使ったRustの概念

### 1. serde によるデシリアライズ

`manifest.json` を読み込んで構造体に変換するのに `serde` を使った。`#[derive(Deserialize)]` を付けるだけで JSON → 構造体の変換が自動化される。

```rust
#[derive(Debug, Deserialize)]
pub struct Manifest {
    pub nodes: HashMap<String, Node>,
    pub parent_map: HashMap<String, Vec<String>>,
    pub child_map: HashMap<String, Vec<String>>,
}
```

`serde_json::from_reader` を使うとファイルをストリームとして読むのでメモリ効率が良い（大きな `manifest.json` でも問題なく動く）。

```rust
pub fn load(path: &Path) -> Result<Manifest, ImpactError> {
    let file = std::fs::File::open(path)
        .map_err(|_| ImpactError::ManifestNotFound(path.to_path_buf()))?;
    let manifest = serde_json::from_reader(file)?;
    Ok(manifest)
}
```

### 2. Result と ? 演算子

Rustにはtry/catchがなく、エラーは `Result<T, E>` 型で表現する。`?` 演算子を付けると、`Err` の場合は即座に呼び出し元に返してくれる。

上の `load` 関数で言えば：

- `File::open` が失敗 → `.map_err()` でカスタムエラーに変換して `?` で返す
- `from_reader` が失敗 → `?` でそのまま返す（`serde_json::Error` → `ImpactError` への変換は `thiserror` が自動でやってくれる）

`Result` のエラー型を `thiserror` で定義するとこうなる：

```rust
#[derive(Debug, thiserror::Error)]
pub enum ImpactError {
    #[error("manifest not found: {0}")]
    ManifestNotFound(PathBuf),

    #[error("failed to parse manifest: {0}")]
    ParseError(#[from] serde_json::Error),

    #[error("model not found: {0}")]
    ModelNotFound(String),
}
```

`#[from]` を付けると `?` での型変換が自動化される。

### 3. BFS（幅優先探索）で依存グラフを走査

`child_map`（下流）または `parent_map`（上流）を BFS で走査する実装。`VecDeque` をキューとして使い、`HashSet` で訪問済みを管理する。

```rust
fn bfs(
    &self,
    name: &str,
    depth: Option<usize>,
    map: &HashMap<String, Vec<String>>,
) -> Vec<(String, usize)> {
    use std::collections::{HashSet, VecDeque};

    let mut visited = HashSet::new();
    let mut queue = VecDeque::new();
    let mut result = vec![];

    queue.push_back((root.to_string(), 0));

    while let Some((node, d)) = queue.pop_front() {
        if visited.contains(&node) {
            continue;
        }
        visited.insert(node.clone());
        result.push((node.clone(), d));

        // depth制限チェック（let-chain: Rust 1.80+）
        if let Some(max) = depth
            && d >= max
        {
            continue;
        }

        if let Some(elements) = map.get(&node) {
            for element in elements {
                queue.push_back((element.clone(), d + 1));
            }
        }
    }
    result
}
```

`depth` は `Option<usize>` で受け取り、`None` なら制限なし・`Some(n)` なら深さ n までという設計。深さ制限に達したノードで `break` でなく `continue` を使っているのは、そのノード自身は結果に含めつつ子のエンキューだけをスキップするため。

**let-chain**（`if let Some(max) = depth && d >= max`）はRust 1.80から安定化された書き方で、`if let` とその他の条件を `&&` でつなげる。以前は `if let` でネストするしかなかったが、これで1行で書ける。

### 4. トレイトと動的ディスパッチ

出力フォーマット（list / tree / json）の切り替えに `Formatter` トレイトを使った。

```rust
pub trait Formatter {
    fn format(&self, root: &str, nodes: &[(String, usize)]) -> String;
}

// main.rs での選択
let formatter: Box<dyn Formatter> = match format.as_str() {
    "tree" => Box::new(TreeFormatter),
    "json" => Box::new(JsonFormatter),
    _      => Box::new(ListFormatter),
};
print!("{}", formatter.format(&model, &result));
```

`Box<dyn Formatter>` はトレイトオブジェクトで、実行時にどの実装を呼ぶかが決まる（動的ディスパッチ）。新しいフォーマットを追加したいときは `Formatter` を実装した構造体を作るだけで、`main.rs` の `match` に1行足すだけで対応できる。

## clippy / rustfmt でコードを磨く

機能を実装した後、`cargo clippy` と `cargo fmt` でコードの品質を高めた。最初の実装から3回コミットでclippyの指摘を全部つぶした。

代表的な修正例：

**before（冗長なif）:**

```rust
if let Some(max) = depth {
    if d >= max {
        continue;
    }
}
```

**after（let-chainに統合）:**

```rust
if let Some(max) = depth
    && d >= max
{
    continue;
}
```

**before（needless borrow）:**

```rust
nodes.keys().find(|k| k.ends_with(&format!(".{name}")))
```

**after（参照不要）:**

```rust
nodes.keys().find(|k| k.ends_with(&format!(".{name}")))
// → clippy が "needless borrow" を指摘 → &format!() の & を外す
```

clippyはRustらしい書き方を教えてくれる先生でもある。Claude君のフィードバックとclippyを組み合わせると、「動くコード」から「Rustらしいコード」への距離が縮まる。

## 振り返り

### Claude Code Learning modeを使った学習の効果

良かった点：

- **詰まったところを即解決できる** — 所有権でハマったとき、自分の言語経験（Java）との差分を踏まえた説明をしてもらえた
- **練習問題のカスタマイズ** — 自分のペースや理解度に合わせた問題を作ってもらえる
- **設計の壁打ち相手になる** — アプリの設計を一緒に考えてもらい、モジュール分割の判断をスムーズにできた

気をつけた点：

- 最初からAIに頼ると「言われた通りに書くだけ」になりやすい。まず自分で教材を読んでコンセプトを理解してから、練習や壁打ちにAIを使うのがよかった

### 今後

業務で実際に使えるツールを作れたことで、Rustを書く動機が続いている。今後は：

- **dbt-impact の機能拡充** — フォーマット追加、manifest.json以外のdbt成果物への対応
- **他のOSSへの参加** — 学んだことを実際のコードベースで試す
- **次のRustプロジェクト** — 業務の別の課題をRustで解決する

Rustの所有権モデルは最初は壁に感じるが、「なぜそうなっているか」を理解すると書いていて気持ちいい言語になる。Learning modeのClaude君と一緒に学ぶのはその「なぜ」を掘り下げるのに向いていた。
