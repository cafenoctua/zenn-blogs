## はじめに

Rustを学ぼうと思うたびに同じ問題にぶつかる。学習を再開したとき「前回どこまで理解したか」が思い出せない。ノートを書こうとしても、実装の合間にまとめる気力がない。

そこで「Claude Codeに学習記録を自動生成させるAgent Skillを作る」ことにした。セッション終了時に `/rust-log` と叩くだけで、会話の内容からClaudeが学習ログを整理・保存してくれる仕組みだ。

さらにそのスキルを使いながら、学習ログをスキャンしてAPIで提供する**study-log-api**をRustで実装した。「Claude Codeで学習効率を上げる仕組みを作りながら、Rustを実装する」という二重構造のプロジェクトになった。

## Claude Code Agent Skillsで学習ログを自動化する

### `/rust-log`スキルとは何か

Claude Codeのカスタムスキルは、プロジェクト直下の`.claude/skills/<スキル名>/SKILL.md`にMarkdownで定義する。ファイルを置くだけで`/rust-log`コマンドとして使えるようになる。

```markdown
---
name: rust-log
description: Rust 学習セッションの内容をログファイルに保存する。/rust-log が呼ばれたとき、
  またはセッション終了時に「ログを残して」「記録して」「まとめて」と言われたときに必ず使う。
---

# Rust 学習ログ記録スキル

今日の Rust 学習セッションの内容を `.claude/session/rust-learning-YYYY-MM-DD.md` に保存する。

## 手順

### Step 1: 日付を取得する
### Step 2: セッションを振り返る（学習したトピック・理解できたこと・つまずいたこと・書いたコード・参照ドキュメント）
### Step 3: 保存先ディレクトリを確認する
### Step 4: ファイル内容をユーザーに提示して承認を得る
### Step 5: 承認後に保存し、完了を報告する
```

フローは「会話履歴を振り返る → フォーマットに整理 → ユーザーに提示して承認 → 保存」の4ステップ。Learningモードと組み合わせて「Claudeがファイル変更前に内容を提示し確認を求める」ようにしてある。

### 実際に生成されたログの例

Day 1のログ（`rust-learning-2026-05-10.md`）の抜粋を示す。

```markdown
# Rust 学習ログ: 2026-05-10

## 学習したトピック
- thiserror を使ったエラー型定義（AppError）
- Axum の IntoResponse トレイト実装
- Rust の所有権と match self vs match &self の違い

## つまずいたこと・疑問点
- match &self を match self に変更後、self.to_string() が使えなくなった
  → to_string() を match より前に取ることで解決
```

自分でメモを書くのではなく、会話の文脈からClaudeが整理してくれる。実装で手を動かしながら「後でまとめよう」と思いつつ忘れる、というループが断ち切れた。

### `.gitignore`でプライベートに保つ設計

`.claude/session/`ディレクトリは`.gitignore`で除外している。試行錯誤の過程や「なぜ？」という疑問をそのまま残せる個人的なメモ帳として機能する。

## 実装したもの：study-log-apiの全体像

学習ログ（Markdownファイル）をスキャンしてDBに格納し、REST APIで提供するWebサービス。`POST /scan`でファイルを読み込み、`GET /logs`で一覧を返す。

| エンドポイント | 説明 |
|---|---|
| GET /health | ヘルスチェック |
| GET /logs | セッション一覧（?date=&keyword=でフィルタ） |
| GET /logs/{id} | セッション詳細 |
| GET /summary | 統計（総セッション数・トピック数・完了数） |
| POST /scan | Markdownファイルをスキャン→DB登録 |

```
src/
├── main.rs          # Axumルータ + テスト
├── error.rs         # AppError（thiserror + IntoResponse）
├── db.rs            # SqlitePool初期化 + マイグレーション
├── scanner.rs       # tokio::fsでのファイルスキャン + パース
├── models.rs        # DB行 ↔ API応答型
└── handlers/
    ├── logs.rs      # GET /logs, GET /logs/{id}
    ├── scan.rs      # POST /scan
    └── summary.rs   # GET /summary
```

技術スタック: **Axum 0.8**（Webフレームワーク）/ **Tokio**（非同期ランタイム）/ **SQLite + SQLx 0.8**（DB）/ **thiserror**（エラー処理）

## 5日間の実装プロセスと学び

各セッションの実装はClaude Codeに設計させた`implementation-plan.md`を起点にしている。「Step N: ○○の実装」という順序がそのまま学習カリキュラムになった。詰まったら「正解ではなくヒント」をClaudeに求める、というスタイルで進めた。

### Day 1 (05-10): Axumの起動とエラー設計

最初のつまずきは所有権だった。`AppError`に`IntoResponse`を実装するとき、`match self`にした後で`self.to_string()`を呼ぼうとしてコンパイルエラーになった。

`into_response(self)`は所有権を受け取る。`match self`でバリアントに分解した後は`self`が使えない。解決策は`match`より前に`to_string()`を呼んでおくことだった。

```rust
impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let message = self.to_string(); // match より前に取る
        let status = match self {
            AppError::LogNotFound(_) => StatusCode::NOT_FOUND,
            AppError::Database(_) => StatusCode::INTERNAL_SERVER_ERROR,
            // ...
        };
        (status, Json(json!({ "error": message }))).into_response()
    }
}
```

「所有権がある」という概念は知っていても、実際にエラーになって理由を理解するまでに時間がかかった。Claudeに「なぜmatch後にself.to_string()が使えなくなるか」を説明させることで概念として定着した。

### Day 2 (05-12): SQLiteと依存注入の「鶏と卵」問題

`sqlx::query_as!`マクロはコンパイル時にDBへ接続してSQLを検証する。つまりDBファイルが先に存在しないと`cargo check`が通らない。

DBファイルを作るには`cargo run`が必要で、`cargo run`するには`cargo check`が通る必要がある——という鶏と卵問題だ。解決策は`sqlx-cli`を使ってあらかじめDBファイルとテーブルを作ること。

```bash
sqlx database create
sqlx migrate run
```

この順序さえ知っていれば詰まらない。しかしRust初学者はマクロがコンパイル時にDBへアクセスするという挙動を知らないため、なぜ`cargo check`が落ちるのかわからないまま時間を使ってしまう。

`with_state(pool)`によるAxumの依存注入パターンも、「ルータにpoolをバインドしてハンドラに渡す」という理解で整理できた。マイグレーション設定ではなくDIの仕組みだ。

### Day 3 (05-14): QueryBuilderで動的SQLを安全に組み立てる

`GET /logs`はクエリパラメータ`?date=`と`?keyword=`を組み合わせてフィルタする。SQLをどう動的に組み立てるかが課題だった。

sqlxの`QueryBuilder`は`push`（SQL構造）と`push_bind`（データ）を分離することでSQLインジェクションを防ぐ。

```rust
let mut qb = QueryBuilder::new("SELECT id, title, date FROM sessions WHERE 1=1");
if let Some(d) = &params.date {
    qb.push(" AND date = ").push_bind(d);
}
if let Some(kw) = &params.keyword {
    qb.push(" AND content LIKE ").push_bind(format!("%{}%", kw));
}
```

`push_bind`を使った時点でプレースホルダー`?`経由が強制される。`format!("%{}%", kw)`はLIKEのワイルドカード付与であり、SQLインジェクション対策ではない（`push_bind`が対策している）。この区別が当初あやふやだったが、Claudeに仕組みを説明させることで理解が整理された。

### Day 4 (05-24): `tokio::fs`で非同期ファイル走査

スキャナーの実装でRustの非同期I/Oを初めて実感した。`std::fs::read_dir`の代わりに`tokio::fs::read_dir`を使い、ループの各ステップで`.await`する。

```rust
let mut entries = tokio::fs::read_dir(dir).await?;
while let Some(entry) = entries.next_entry().await? {
    let path = entry.path();
    if path.extension().and_then(|e| e.to_str()) != Some("md") {
        continue;
    }
    let content = tokio::fs::read_to_string(&path).await?;
    upsert_session(pool, &path, &content).await?;
}
```

`.await`のたびに他のタスクへ制御が渡る。ループ1回ごとにI/Oを非同期で処理しながら、スレッドをブロックしない。`async/await`の実際の動きを手を動かして感じた瞬間だった。

また`AppState`パターンで`SqlitePool`に加えて`session_dir`や`topics_file`をまとめ、環境変数で注入できるようにした。ハンドラの`State`型を`SqlitePool`から`AppState`に変えると既存ハンドラ全部の型を直す必要があり、`cargo check`の警告に助けられながら修正した。

### Day 5 (05-31): `#[sqlx::test]`でインメモリDBテスト

`#[sqlx::test]`アトリビュートを付けるだけで、インメモリDBの生成・マイグレーション実行・テスト後クリーンアップを全自動でやってくれる。テスト用DBのセットアップをほぼ書かなくていい。

Axumハンドラのテストは`tower::ServiceExt::oneshot`で実際にHTTPリクエストを送る`make_app`パターンで書いた。

```rust
#[sqlx::test]
async fn test_get_logs_not_exists_id(pool: SqlitePool) {
    let app = make_app(pool);
    let req = Request::builder()
        .uri("/logs/9999")
        .body(Body::empty())
        .unwrap();
    let res = app.oneshot(req).await.unwrap();
    assert_eq!(res.status(), StatusCode::NOT_FOUND);
}
```

所有権で詰まった箇所があった。`make_app(pool)`が`pool`の所有権を奪うため、その後で`INSERT`した行の`last_insert_rowid()`を取得しようとしてコンパイルエラーになった。`INSERT`→`last_insert_rowid()`→`make_app(pool)`という順序に変えることで解決した。

トレイトスコープルールも壁になった。`BodyExt::collect()`を呼ぶには`use http_body_util::BodyExt;`でトレイトをスコープに持ち込む必要がある。メソッドが「存在しない」というエラーが出たとき、まずimportを疑う習慣が付いた。

## Claudeに設計させて読み解く学習スタイルについて

今回の学習フローはこうだった。

1. Claude Codeに`implementation-plan.md`を設計させる
2. 「Step N: ○○の実装」という計画を1ステップずつ読み進める
3. 手を動かす。詰まったら「解答ではなくヒントを」とClaudeに依頼する
4. セッション終了時に`/rust-log`で学習ログを保存する

この方法の利点は**ヒントの粒度を自分で調整できる**ことだ。「方向性だけ教えて」から「このエラーの原因を説明して」まで、理解のレベルに合わせて問い方を変えられる。コードをコピーするのではなく「なぜそうなるか」を理解してから実装するリズムが作れた。

落とし穴は、Rustの所有権のように概念が難しいトピックはコードを見るだけでは足りないことだ。「なぜ`match self`の後に`self`が使えないか」のような質問をClaudeに追加で投げることで、概念として腹落ちした。

Agent Skillsで学習ログを残すと、次のセッション開始時に「前回のログを読んでから始めて」とClaudeに伝えられる。どこまで理解が進んでいるかをClaudeが把握した状態でセッションを始められるため、毎回ゼロから説明し直す手間がなくなる。

## まとめ

この二重構造プロジェクトから得た知見を3点にまとめる。

1. **Agent SkillsはSKILL.mdを書くだけで`/コマンド`として使えるカスタム自動化が作れる**。学習記録の自動化は「メモの手間」を取り除き、継続しやすくする。

2. **Claudeに設計させて読み解きながら実装する学習スタイルは効果的だった**。詰まったらヒントを求め、なぜそうなるかを説明させることで概念として定着する。

3. **Rustのasync/await、Axumのエクストラクタ、SQLxのマクロ、tokio::fsは実装を通じてはじめて実感できた**。特に`#[sqlx::test]`と`#[sqlx::query_as!]`のコンパイル時検証は、Rustらしい「実行前に壊れているものを壊れていると知れる」体験だった。
